# Sabai — โจทย์ตรวจความปลอดภัย (Security Review Brief)

**เป้าหมาย:** ตรวจก่อนเปิดใช้เงินจริง ผลลัพธ์ที่ต้องการ: รายงานช่องโหว่จัดระดับความรุนแรง + ข้อเสนอแก้ + ยืนยันแก้แล้ว (retest) และลงนามในรายการ `go_live_approvals` ฝ่าย SECURITY
**ข้อควรระวัง:** เอกสารนี้ระบุช่องว่างที่ทีมพัฒนารู้ตามจริง ไม่ได้แปลว่าระบบปลอดภัยครบ

## 1) ขอบเขต
- โค้ด: repo `Bas-travel/apptravel` — backend Go (`backend/`), เว็บต้นแบบ React (`apps/web-prototype/`), migrations (`backend/database/migrations/`)
- ระบบที่รันได้: ตามขั้นตอน `backend/docs/run-local.md` (MySQL + API + เว็บ)
- สเปก: `backend/docs/openapi.yaml`, ดีไซน์การเงิน `backend/docs/design/0001–0004`
- **นอกขอบเขต:** แอป Flutter เดิม (ยังไม่ได้ตรวจสอบ/เชื่อมต่อ), โครงสร้างพื้นฐานโปรดักชัน (ยังไม่มี), PSP จริง (ยังไม่เลือก)

## 2) มาตรการที่มีอยู่แล้ว (ให้ผู้ตรวจพิสูจน์ ไม่ใช่เชื่อตาม)
- จำนวนเงินฝั่งเซิร์ฟเวอร์เป็นจำนวนเต็มสตางค์; ไคลเอนต์ไม่คำนวณเงิน
- ตารางการเงินแบบ append-only (มีทริกเกอร์) + audit log แบบ hash-chain
- Idempotency-Key, ล็อกระดับแถว, READ COMMITTED
- Webhook: ตรวจลายเซ็น, หน้าต่างกัน replay, กันเหตุการณ์ซ้ำ
- State machine ของ booking/refund/settlement; แบ่งหน้าที่ (SoD) ผู้เตรียม/ตรวจ/อนุมัติเป็นคนละคน
- JWT + RBAC (`auth.RequirePermission`); ข้อมูลการจอง/กระเป๋าเงินจำกัดเฉพาะเจ้าของ (คนอื่นได้ 404)
- สวิตช์ปลอดภัย: `FINANCIAL_TRANSACTIONS_ENABLED=false`, `PAYMENT_PROVIDER=mock`, `go_live_approvals`
- ตัวจำลองการชำระเงิน `/dev/payments/simulate` มีเฉพาะเมื่อใช้ Mock และ `APP_ENV != prod` (มีเทสต์)
- เลขบัญชีธนาคารพาร์ทเนอร์เก็บแบบเข้ารหัส

## 3) ช่องว่างที่ทราบ (ตรวจแล้วในโค้ด ไม่พบการดำเนินการ)
| รายการ | สถานะ |
|---|---|
| Rate limiting / ป้องกัน brute force / lockout ที่ login | ไม่พบ |
| MFA (โดยเฉพาะบทบาทการเงิน/แอดมิน) | ไม่พบ |
| อายุ JWT 24 ชม., ไม่มี refresh/revocation ที่ยืนยันได้ | ต้องตรวจ |
| bcrypt ใช้ cost ค่าเริ่มต้น | ควรทบทวน |
| Structured logging / การปิดบังข้อมูลใน log | ไม่พบ |
| สแกนช่องโหว่ใน CI (govulncheck, gosec, npm audit, secret scan) | ไม่มี |
| การจัดการ secret/คีย์เข้ารหัส/การหมุนคีย์ในโปรดักชัน | ยังไม่ได้ออกแบบ |
| CORS, security headers, TLS | ตั้งค่า dev เท่านั้น |
| ความปลอดภัยของ dependency ที่ใช้ mirror (`alt.mod`) ในเครื่อง dev | ตรวจว่าไม่ถูกใช้ใน CI/โปรดักชัน |

## 4) หัวข้อที่ขอให้เน้น
1. **การควบคุมสิทธิ์:** IDOR, ยกระดับสิทธิ์ผ่าน role-requests, เส้นทางแอดมิน/การเงิน, การข้าม SoD
2. **ตรรกะการเงิน:** race condition (จ่ายซ้ำ/คืนซ้ำ/จองซ้ำที่นั่ง), การเล่น webhook ซ้ำ, การปลอมลายเซ็น, ข้ามการอนุมัติตามวงเงิน, ทำให้ settlement ติดลบ, ปัดเศษสตางค์
3. **Idempotency:** ใช้คีย์เดียวกับ payload ต่างกัน, ใช้คีย์ข้ามผู้ใช้
4. **Auth:** การเก็บ/อายุโทเค็น, การรีเซ็ตรหัสผ่าน (ถ้ามี), enumeration ผู้ใช้
5. **การฉีดคำสั่ง/ข้อมูล:** SQL, XSS ฝั่งเว็บ, การจัดการข้อมูลนำเข้า (CSV กระทบยอด, seed)
6. **Audit log:** ลองแก้/ลบ/ข้ามห่วงโซ่ hash
7. **ความเป็นส่วนตัว (PDPA):** ข้อมูลส่วนบุคคลใน log/response
8. **สวิตช์ปลอดภัย:** พิสูจน์ว่าเปิดเงินจริงโดยไม่ตั้งใจไม่ได้ และตัวจำลองไม่โผล่ในโปรดักชัน
9. **Supply chain/CI:** workflow, dependency

## 5) วิธีเข้าถึงสภาพแวดล้อมทดสอบ
ทำตาม `backend/docs/run-local.md` → seed ข้อมูล `cmd/seed -yes` (ปฏิเสธ `APP_ENV=prod`) → `scripts/e2e-smoke.sh` ตรวจเส้นทางหลัก ชุดทดสอบ: `go test -race -tags integration ./...` (ต้องมี `MYSQL_TEST_DSN`)

## 6) ผลลัพธ์ที่ส่งมอบ
- รายงานช่องโหว่: ระดับ (CVSS หรือ Critical/High/Med/Low), ขั้นตอนทำซ้ำ, ผลกระทบ, คำแนะนำ
- รอบ retest หลังแก้ และจดหมายสรุปสำหรับฝ่ายกฎหมาย/ผู้บริหาร
- เกณฑ์ผ่านเสนอ: ไม่มี Critical/High ค้าง

## 7) แม่แบบเรียกใบเสนอราคา
> เรียน [บริษัทตรวจความปลอดภัย]
> ขอใบเสนอราคาสำหรับ application security review + penetration test ของแพลตฟอร์มจองท่องเที่ยวที่มีระบบการชำระเงินและจ่ายพาร์ทเนอร์ (Go/MySQL + React) แบบ white-box ตามเอกสารแนบ ขอทราบ: ประสบการณ์ด้านระบบการเงิน/PCI, ระยะเวลา, ราคา, รูปแบบรายงาน, รอบ retest, และการรับรองเมื่อผ่านเกณฑ์ ต้องการเริ่ม [วันที่] และลงนามรับ NDA ก่อนส่งโค้ด

## 8) ที่ทีมพัฒนาควรแก้ก่อนส่งตรวจ (ลดค่าใช้จ่าย)
rate limiting + lockout, ลดอายุโทเค็น, structured logging แบบไม่เก็บข้อมูลลับ, เพิ่ม govulncheck/gosec/npm audit ใน CI
